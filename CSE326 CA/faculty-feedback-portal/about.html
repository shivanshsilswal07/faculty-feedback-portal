About

About this portal

A CA1 academic project built to demonstrate HTML fundamentals, semantic HTML and HTML forms in a realistic setting.

The problem

Course feedback at most institutions is collected on paper at the end of the semester, or through a generic form tool that wasn't designed for academic evaluation. The result is slow collection, inconsistent questions across departments, and data that nobody can easily summarize. Students also hesitate to answer honestly when they aren't sure whether their name is attached.

The solution

This portal puts the whole cycle in one place: a structured rating form built around defined evaluation criteria, an explicit anonymous option, a check that stops the same student submitting twice for the same course, and an administrator dashboard that shows averages and comparisons as visuals rather than raw rows.

Audio introduction

A spoken summary of how to use the portal, provided for students who prefer listening or use screen readers.

Technologies used

HTML5
Page structure, semantic sectioning elements, forms, tables, media elements.
CSS3
Custom properties, Grid, Flexbox, media queries, focus and hover states.
JavaScript
Form validation, dynamic dropdowns, duplicate-submission simulation, chart rendering.
GitHub Pages
Static hosting — no server, no database, no build step.

What this project honestly is — and isn't

Being clear about limitations is part of the project, not a weakness in it.

  • No real authentication. The login page simulates a session using localStorage. Any Student ID and email will "work". Passwords are never stored or verified.
  • No database. Feedback submissions are not sent anywhere. Duplicate-submission prevention writes a flag to the browser's own storage, which the student could clear.
  • Analytics are sample data. The ratings and counts shown on the Analytics and Admin pages are fixed demo values written into script.js.
  • No access control. The Admin Dashboard is reachable by anyone, because static hosting cannot restrict pages.

What a production version would add

  1. A backend server and a real database to store submissions.
  2. Server-side authentication with hashed passwords and session tokens.
  3. Role-based access so only staff reach the admin dashboard.
  4. A server-enforced uniqueness rule on (student, course, faculty) so duplicates cannot be bypassed.
  5. True anonymization, where the identifier is stripped before the response is stored.

Project FAQ

Why no framework?

The CA1 syllabus covers HTML fundamentals and semantic HTML and forms. A framework would hide exactly the concepts being assessed. Everything here is plain HTML, CSS and JavaScript.

Why is localStorage used at all?

Because GitHub Pages serves static files only. localStorage is the simplest way to demonstrate session and duplicate-check behaviour in the browser, and it's clearly labelled as a demonstration everywhere it appears.

Are the faculty names real?

No. All faculty names, courses, ratings and comments are fictional sample data created for this project.
